# Component 20: Documentation Site

## Identity

- **Component number:** 20
- **Name:** Documentation site
- **Module paths:** (this component produces docs and site infrastructure, not source code)
- **Output paths:**
  - `mkdocs.yml` — site configuration (at repo root)
  - `site/` — gitignored build output (the actual generated HTML, not committed)
  - `site_src/` — site source content (Markdown, custom CSS, custom landing page)
  - `site_src/index.html` — custom landing page (the marketing tier)
  - `site_src/docs/` — Material-themed reference content (the docs tier)
  - `site_src/assets/` — images, screenshots, the custom CSS overlay
  - `.github/workflows/docs.yml` — GitHub Pages publishing workflow
- **Roadmap phase:** Phase 5 (second component)
- **Depends on components:**
  - 14 (JSON schema — referenced in docs)
  - 15, 17, 18 (renderers — screenshots and examples come from these)
  - 19 (GitHub Action — the docs link to it and use it as a primary integration example)
- **Depended on by:** 21 (flagship ERA demo — the demo will live as a page on the docs site), every user who adopts owlcompare

## Purpose

Produce a documentation site at `https://ajala111.github.io/owlcompare/` that serves three distinct audiences:

1. **Evaluators** — landing page with value proposition, screenshot, one-line install
2. **Integrators** — getting-started tutorial: install, first diff, common workflows
3. **Depth-seekers** — reference docs: CLI reference, JSON schema, severity rules, rename detection, GitHub Action

After this component, owlcompare has a professional public-facing presence that converts curiosity into adoption.

What would break if we removed it: the README becomes the only documentation; navigation is impossible; new users can't find what they need; the project looks like an unmaintained hobby. Adoption stalls.

## Internal design

### The landing page (`site_src/index.html`)

This is **NOT** a Markdown file. It's hand-written HTML with custom styling that lives outside the MkDocs Material theme. Structure (top to bottom):

1. **Hero section** (full viewport):
   - Wordmark + tagline ("Diff OWL/RDF ontologies, find what really changed")
   - One-line value proposition ("owlcompare goes beyond triple-level diff — surfaces renames, restriction changes, severity classification, and rename detection")
   - Primary CTA: "Get started" button → links to `/getting-started/installation/`
   - Secondary CTA: "View on GitHub" button
   - Background: subtle gradient or pattern, NOT a photo

2. **"See it in action" section**:
   - A screenshot of the HTML report (Component 17's actual output)
   - Below: a screenshot of a PR-comment Markdown render
   - Caption: "Three output formats: terminal, beautiful HTML, PR-comment-ready Markdown, plus JSON and JUnit XML for automation"

3. **"What makes it different" section** (three columns):
   - Column 1: "Beyond triple-level diff" — explains the 4-layer model briefly
   - Column 2: "Smart rename detection" — explains rename detection
   - Column 3: "CI-ready" — explains the GitHub Action

4. **"Install in 30 seconds" section**:
   - Tabbed code block showing `pip install owlcompare`, `uv add owlcompare`, GitHub Action YAML
   - Below: a `bash` command showing a first diff

5. **"Real-world example" section**:
   - A code block showing the era_evolution diff output (or any compelling real example)
   - The reduction from "18 raw triple changes" to "5 meaningful events" framed prominently

6. **Footer**:
   - Links: Docs · GitHub · Issues · MIT License
   - "Built by [phelz]" credit
   - No tracking, no analytics in v1

The landing page is a **single self-contained HTML file** with inline CSS and minimal JS (just for the install-method tab switcher). NO external dependencies (no Google Fonts, no analytics, no CDN). It must work offline if downloaded.

### Content authoring approach

For each docs page, the rule is:

**Don't auto-generate from source code.** Don't use `mkdocstrings` or similar to ingest Python docstrings. The audience for this site is *users*, not developers reading source. User-facing docs are deliberately separate from internal source documentation.

Each page is hand-written Markdown. The tradeoff: more upfront work, but the content is structured for users, not for code-doc generators.

### Page-by-page content brief

For each page, the spec includes a one-paragraph brief of what the page should contain. These are intentionally short — full content is written during implementation, but the briefs anchor scope.

**Getting Started / Installation:**
Install via pip and via the GitHub Action. Verify the install works. Troubleshoot common installation errors (Python version, missing tools).

**Getting Started / First Diff:**
A walkthrough using two minimal example ontology files committed to the repo (e.g., `examples/before.ttl`, `examples/after.ttl`). Run the command, observe output, understand what each line means. ~10-minute exercise.

**Getting Started / Understanding Output:**
Explain the 4-layer diff model briefly. Explain severity (breaking vs non_breaking vs additive vs info). Explain renames. Pointer to deeper docs.

**Getting Started / Next Steps:**
Pointer to: CI integration, severity overrides, rename detection, the GitHub Action.

**Guides / CI Integration:**
The three-line GitHub Action setup. Examples for GitLab CI, Jenkins. Configuring `fail-on-breaking`. PR comment integration.

**Guides / Severity Overrides:**
The TOML config format. Common scenarios: "ignore all annotation changes," "treat reparents as breaking," "downgrade specific entities." Cross-link to reference/severity-rules.md.

**Guides / Rename Detection:**
Three confidence tiers explained with examples. When to use `--rename-confidence medium`. The TOML mapping file. The `--export-rename-mapping` workflow.

**Guides / Reading the HTML Report:**
A tour of the HTML report. What each section means. How to use the toolbar. The download-JSON workflow.

**Guides / Working with Large Ontologies:**
Performance considerations. The 2000-changes-under-5MB benchmark. When to use selective diffing.

**Reference / CLI:**
Every command, every flag. Use `typer`'s `--help` output as a starting point but rewrite for clarity. Include 2-3 examples per command.

**Reference / JSON Schema:**
Link to the bundled schema file. Explain each top-level field. Document the schema versioning policy.

**Reference / Severity Rules:**
The 6 built-in rules from Component 10. The override format. Severity color/label mapping.

**Reference / Change Kinds:**
Every emitted Change kind documented. Categorized by layer and pattern. Cross-references to the slice that emits each one.

**Reference / Exit Codes:**
The full exit code table: 0 (success), 1 (general error), 2 (usage), 3 (load error), 4 (file not found), 5 (write error), 6 (config error), 10 (breaking changes detected). Document each.

**Architecture / Overview:**
The 4-layer model. Pipeline flow diagram. Canonicalization. Severity post-processing. Component breakdown.

**Architecture / Diff Layers:**
Detailed per-layer documentation. Drawn from specs 05-09 but rewritten for user comprehension.

**Architecture / Rename Detection Internals:**
The detection algorithm. Confidence scoring. Cascade consolidation. The DD-018 fix (Component 12).

**Architecture / Canonicalization:**
RDFC-1.0. Restriction reification. List collapsing. Anonymous structure decoding (Component 12.5).

**FAQ:**

- "Does owlcompare support OWL2 reasoning?"
- "Can I diff ontologies that import each other?"
- "What's the performance ceiling?"
- "Is owlcompare a stable v1 API?"

**Changelog:**
Release notes. v0.0.1 (initial release) is the first entry. Auto-updated from git tags.

### Publishing pipeline (`.github/workflows/docs.yml`)

A workflow that:

1. Triggers on push to `main` (where docs sources change) AND on manual `workflow_dispatch`
2. Sets up Python 3.11, installs `mkdocs-material` (plus the small set of plugins listed in `mkdocs.yml`)
3. Builds the site: `mkdocs build --strict --clean`
4. Copies `site_src/index.html` and `site_src/assets/` into the `site/` output (preserving directory structure) so the custom landing page is served alongside the Material-built docs
5. Uploads the `site/` directory as a Pages artifact via `actions/upload-pages-artifact@v3`
6. Deploys to GitHub Pages via `actions/deploy-pages@v4`

The `--strict` flag fails the build on broken internal links — the cheapest way to catch link rot in docs.

The workflow runs only on push to main (not on every PR — preview builds are out of scope for v1). The artifact is signed by GitHub, so we don't need a custom domain or SSL setup.

### Screenshots

Two are critical for the landing page:

1. **`screenshot-html.png`** — a real owlcompare HTML report screenshot. Captured by:
   - Running `owlcompare diff <era_evolution_v1.ttl> <era_evolution_v2.ttl> --format html --out tmp.html`
   - Opening `tmp.html` in Chrome at 1440x900 viewport
   - Capturing the visible area (or scrolling and using Chrome's "Capture full size screenshot")
   - Saving as PNG, 2x DPI for retina displays

2. **`screenshot-pr.png`** — a PR comment showing the Markdown render. Captured by:
   - Posting the Markdown output to a real GitHub PR (could be a draft PR in the owlcompare repo itself)
   - Screenshotting the rendered comment

These should be regenerated when the HTML/Markdown rendering changes (e.g., after a major UI revision). Document this in the contributing guide.

### Landing page hosting strategy

The landing page (`site_src/index.html`) is served at the site root (`/`). The Material docs are at `/docs/` (or sub-paths). The MkDocs nav links go directly to docs sub-paths.

When a user clicks "Docs" in the landing page, they go to `/getting-started/installation/`.

When MkDocs builds, the Material theme tries to put its own index at `/`. We override this by overwriting the built `site/index.html` with our custom landing page during the workflow's "publish" step.

If MkDocs Material complains about a missing docs index, create `site_src/docs/index.md` as a minimal redirect or breadcrumb page that pre-empts the issue.

## Edge cases & failure modes

- **Build fails on `mkdocs build --strict` due to a broken link:** the link target must be fixed; this is intentional. The build won't publish until the link is fixed.
- **GitHub Pages deployment fails:** check the `Pages` settings in the repo (Settings → Pages → Source: GitHub Actions). Document this in `docs/contributing.md`.
- **The custom landing page conflicts with MkDocs Material:** documented above; the publish step overwrites `site/index.html` after build.
- **Screenshots become out of date:** add a documentation note in `docs/contributing.md` reminding contributors to regenerate screenshots when UI changes. No automated detection.
- **Search returns no results for technical terms:** the Material theme's search is fuzzy and indexes all content. If users report missing terms, add them to page content with explicit prose.
- **Mobile rendering:** Material is mobile-responsive by default. The landing page must also be tested mobile (the install command tabs and the screenshots need to render well at narrow widths).
- **Print stylesheets:** Material provides reasonable print styles. Verify with browser print preview.
- **Accessibility:** Material is WCAG AA compliant by default. Don't override in a way that breaks compliance. The custom landing page must independently pass WCAG AA.

## Dependencies

- **`mkdocs`** — the static site generator (Python package)
- **`mkdocs-material`** — the Material theme (Python package)
- **`pymdown-extensions`** — Markdown extensions used by `mkdocs.yml`

These are added to `pyproject.toml` as an optional dependency group:

```toml
[dependency-groups]
docs = [
    "mkdocs>=1.6",
    "mkdocs-material>=9.5",
    "pymdown-extensions>=10.7",
]
```

Users running `uv sync --group docs` can build the site locally. The default `uv sync` doesn't install these.

The docs CI workflow installs only the `docs` group: `uv sync --only-group docs`.

- **Versioned documentation.** v1 ships a single live version. Versioning (`mike` plugin) is v1.1.

- **PDF export of docs.** MkDocs Material has a plugin for this; defer to v1.1.

- **Newsletter signup.** Not in v1.

## Open questions

- [ ] **Q1:** Should the landing page link to a hosted live HTML report (e.g., a permalink to `examples/era_evolution_report.html` hosted on the docs site)?
  **Proposed:** Yes. Host two sample reports at `/examples/era_evolution.html` and `/examples/era_renames.html`.   **Proposed:** Yes, but as a single FAQ entry rather than a dedicated page. Comparison content is contentious and dates badly; a single focused FAQ entry ("How is owlcompare different from ROBOT diff?") is enough to answer the natural question without committing to an exhaustive comparison matrix.

- [ ] **Q3:** Should the docs site use a custom domain (e.g., `owlcompare.dev`)?
  **Resolved:** No, not in v1. `ajala111.github.io/owlcompare/` is the published URL; works immediately, no configuration needed. A custom domain is a v1.1 polish item.
