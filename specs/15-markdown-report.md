# Component 15: Markdown Report

## Identity

- **Component number:** 15
- **Name:** Markdown report (PR-comment ready)
- **Module paths:**
  - `src/owlcompare/report/__init__.py` — the report package root (created here for the first time; Phase 4 will populate it further)
  - `src/owlcompare/report/markdown_report.py` — this component's implementation
  - `src/owlcompare/report/_markdown_helpers.py` — small text-formatting helpers (escaping, severity icons, IRI prefixing for Markdown)
- **Roadmap phase:** Phase 4 (second component)
- **Depends on components:** 14 (JSON schema — Markdown rendering reads from a known shape), 11/12 (rename Change kinds), 06–09 (Layer 1 kinds)
- **Depended on by (planned):** 19 (GitHub Action — uses Markdown for PR comments)

## Purpose

Produce a Markdown report of a `DiffResult` suitable for posting as a PR comment, archiving as a file, or reading in any Markdown viewer. The report uses severity-driven sectioning, emoji indicators, and a collapsible "unexplained Layer 0" section, prioritizing scannability in narrow rendering contexts (GitHub PR comments are 600–800px wide).

What would break if we removed it: every CI integration that wants to surface diff results in PR comments would have to either reimplement Markdown rendering from JSON or post the JSON itself (unreadable in a PR view). Workflow integration would stall.

## Inputs

| Input | Type | Source | Notes |
|-------|------|--------|-------|
| Diff result | `DiffResult` | Orchestrator output | Final, severity-refined, rename-consolidated |
| Snapshot metadata | from `result.a`, `result.b` | For display ("Comparing X vs Y") | Source paths or IRIs |
| Options | `MarkdownOptions` | Optional | Knobs for verbosity, footer, etc. |

## Outputs

| Output | Type | Consumer | Notes |
|--------|------|----------|-------|
| Markdown text | `str` | CLI stdout / file | UTF-8, no leading/trailing whitespace |

## Public API

```python
# src/owlcompare/report/markdown_report.py

from dataclasses import dataclass
from .._common import DiffResult


@dataclass(frozen=True, slots=True)
class MarkdownOptions:
    """Configuration for Markdown rendering."""
    include_footer: bool = True            # The "Generated by owlcompare" attribution
    include_layer0_collapsed: bool = True  # The <details> block for unsubsumed Layer 0
    max_changes_per_section: int = 50      # Truncate long sections with "...and N more"
    emoji_style: str = "github"            # 'github' for 🔴🟡🟢⚪ ✏️; 'plain' for [BREAKING], [WARN], etc.
    heading_level: int = 2                 # Top heading level (h2 by default; CI may want h3)


def render(
    result: DiffResult,
    options: MarkdownOptions | None = None,
) -> str:
    """Render a DiffResult as Markdown.

    Returns the full Markdown document as a string. The caller decides
    where to write it (stdout, file, HTTP API).
    """
```

## CLI integration

`--format markdown` becomes a real option (previously the `diff` subcommand only supported `json` and `text`).

```
owlcompare diff [OPTIONS] ONTOLOGY_A ONTOLOGY_B

  --format [json|text|markdown]    Output format
  --out PATH                       Write output to file instead of stdout
  --markdown-heading-level INT     Top-level heading depth (default 2; 1-4 valid)
  --no-markdown-emoji              Use plain-text severity tags instead of emoji
                                   (e.g., [BREAKING] instead of 🔴)
```

When `--format markdown` is set, render with `markdown_report.render()` and write to stdout (or `--out PATH`). Other format-specific flags are ignored.

The `--validate-schema` flag from Component 14 has no effect for Markdown output.

## Internal design

### Document structure

The Markdown document follows this fixed shape (sections omitted if empty):

```
{heading} owlcompare diff: {severity_summary}

Compared `{source_a}` against `{source_b}`.

{renames_section}

{breaking_section}

{other_changes_section}

{layer0_unexplained_collapsed}

{footer}
```

Where:

- `{heading}` is `##` by default (configurable via `heading_level`)
- `{severity_summary}` is `"N breaking changes"`, `"only non-breaking changes"`, `"no changes"`, etc.
- `{source_a}`/`{source_b}` are the source descriptions (file paths, URLs, or "ontology A" if no source string)

### Severity summary phrasing

The h2 title carries an at-a-glance status. Logic:

| Condition | Title phrasing |
|-----------|----------------|
| `breaking > 0` | `🔴 owlcompare diff: N breaking changes` (N=count) |
| `breaking == 0`, total > 0 | `🟢 owlcompare diff: no breaking changes` |
| `total == 0` | `⚪ owlcompare diff: no changes` |

With `--no-markdown-emoji`, the emoji is replaced by `[BREAKING]`, `[OK]`, `[NONE]` respectively.

### Sectioning rules

Each section is rendered as `### {section_title} ({count})` followed by a bulleted list. Sections are emitted *only if non-empty*.

**Section: Renames (if any rename changes present)**

```markdown
### Renames (3)

- ✏️ Class renamed: `era:Track` → `era:RailwayTrack` *(high confidence — matching label "Track"@en)*
- ✏️ Class renamed: `era:Signal` → `era:RailwaySignal` *(certain — user mapping)*
- ✏️ Object property renamed: `era:locatedOn` → `era:hasLocation` *(high confidence — matching label "located on"@en)*
```

Each rename includes its confidence and a short evidence summary. Cascade subsumption is not detailed in the bullet (full evidence available in JSON).

**Section: Breaking changes (severity = 'breaking')**

```markdown
### Breaking changes (1)

- 🔴 **Object property removed:** `era:locatedOn` *"located on"@en*
```

Each line: emoji, bold label, the change subject in code formatting, optional info in italics.

**Section: Other changes (severity = 'non_breaking', 'additive', or 'info')**

```markdown
### Other changes (3)

- 🟡 Restriction relaxed on `era:Track`: `era:hasMaxSpeed max 1 → max 2`
- 🟢 Class added: `era:Platform` *"Platform"@en*
- ⚪ Label changed on `era:Track` (fr): *"Voie"* → *"Voie ferrée"*
```

Emoji per severity:
- 🔴 breaking
- 🟡 non_breaking
- 🟢 additive
- ⚪ info
- ✏️ rename (any confidence)

In `--no-markdown-emoji` mode, replace with `[BREAKING]`, `[NON-BREAKING]`, `[ADDITIVE]`, `[INFO]`, `[RENAME]` prefixes.

### Per-kind summary formatting

Each Change kind needs a specific Markdown rendering. These are the templates:

| Kind | Template |
|------|----------|
| `class_added`/`class_removed` | `**Class {action}:** ` `` `{iri}` `` ` *"{label}"@{lang}*` |
| `object_property_*`/`data_property_*`/etc. | Same pattern, "Object property added", etc. |
| `class_parent_added` | `**Class parent added:** ` `` `{child}` `` ` gained ` `` `{parent}` `` |
| `class_parent_removed` | `**Class parent removed:** ` `` `{child}` `` ` lost ` `` `{parent}` `` |
| `class_reparented` | `**Class reparented:** ` `` `{child}` `` `: {old} → {new} ({direction})` |
| `restriction_added` | `**Restriction added on** ` `` `{entity}` ``: `` `{readable_form}` `` |
| `restriction_removed` | `**Restriction removed from** ` `` `{entity}` ``: `` `{readable_form}` `` |
| `restriction_changed` | `**Restriction changed on** ` `` `{entity}` ``: `` `{before_form} → {after_form}` `` |
| `domain_changed`/`range_changed` | `**Domain changed on** ` `` `{property}` ``: `{before} → {after}` |
| `equivalent_class_added` | `**Equivalent class added:** ` `` `{entity}` `` ` ≡ ` `` `{other}` `` |
| `disjoint_added` | `**Disjoint with added:** ` `` `{entity}` `` ` ⊥ ` `` `{other}` `` |
| `entity_deprecated` | `**Deprecated:** ` `` `{entity}` `` |
| `annotation_changed` | `**Label changed** on ` `` `{entity}` `` ` ({lang}): *"{before}"* → *"{after}"*` (or `Comment changed` for `rdfs:comment`) |
| `ontology_metadata_changed` | `**Ontology metadata:** ` `` `{predicate}` `` ` *"{before}"* → *"{after}"*` |
| `class_renamed` | `**Class renamed:** ` `` `{before}` `` ` → ` `` `{after}` `` ` *({confidence} — {evidence_summary})*` |

A central function `_format_change(change)` returns the bullet body string for any kind. Unknown kinds fall back to `change.summary` from the producer.

### IRI shortening

In Markdown bullets, prefer prefixed IRIs (`era:Track`) over full IRIs (`http://data.europa.eu/949/Track`) when the prefix is known from the snapshot's namespace bindings. Wrap in backticks.

For *unknown* prefixes, use the full IRI in backticks. Don't try to shorten generically.

Restriction URN shortening (`_restriction:abc12345`) from Component 05's helper is reused.

### Unexplained Layer 0 collapsed section

If there are any non-subsumed Layer 0 changes, append:

```markdown
<details>
<summary>📜 {count} unexplained Layer 0 changes</summary>

- 🔴 Removed: ` `` `triple representation` `` ``
- ...
</details>
```

GitHub renders `<details>`/`<summary>` natively. Other Markdown renderers may not — that's acceptable degradation (the section just appears as plain text).

If there are zero unexplained Layer 0 changes, the section is omitted entirely (no empty `<details>` block).

### Footer

```markdown
---
*Generated by owlcompare {version} · [Schema](docs/schema/diff-result.schema.json) · [JSON output available]*
```

Where `{version}` is read from `owlcompare.__version__`. The Schema link points at the bundled schema file (relative path works in GitHub; in other contexts it's just a textual reference).

If `options.include_footer = False`, the footer is omitted entirely.

### Truncation

If any section has more than `max_changes_per_section` (default 50) bullets, truncate with:

```markdown
- ...and {n} more (see JSON output for full list)
```

50 is high enough that most real diffs aren't truncated; the truncation exists for pathological cases.

### Special character escaping

User-supplied content (labels, comments, IRIs) may contain Markdown special characters. Escape:
- `*`, `_`, `~`, `` ` ``, `[`, `]`, `(`, `)`, `<`, `>`, `\`, `|` within bullet text
- Preserve them inside backtick-wrapped code spans (where they don't need escaping)

A helper `escape_markdown(s: str) -> str` handles this. Test with labels containing each character.

### Line wrapping

Don't pre-wrap lines. Markdown renderers handle their own wrapping. Long bullets will wrap to multiple visual lines but stay one logical bullet.

## Edge cases & failure modes

- **Empty diff (no changes at all):** render just the title (`🟢 owlcompare diff: no changes`), the "Compared" line, and the footer. No sections.
- **Only Layer 0 changes (everything unexplained):** this is rare post-rename-detection, but possible. Render the unexplained section without an "Other changes" section.
- **All changes are renames:** render only the Renames section. Title says "no breaking changes" (renames are info).
- **A change with no `details.label`:** render without the italic label suffix.
- **A change whose `subject` is `None`:** render `<unknown>` (placeholder). Should be rare; mostly Layer 0 with blank node subjects.
- **`source_a == source_b` (rare; means user diffed a file against itself):** render with both names; title shows "no changes."
- **Source path contains backticks or other Markdown specials:** escape via `escape_markdown`.
- **Restriction summaries with synthetic URNs:** rendered as `_restriction:abc12345` (already handled by Component 05's helper).
- **Very long labels** (>200 chars): keep as-is. Markdown renderers will wrap.
- **HTML in user-supplied labels:** escape `<`, `>` so it renders as text, not as HTML tags.
- **`heading_level` invalid** (5, 6, 0, -1): default to 2 silently. Don't fail; the spec is permissive.

## Out of scope (deliberately)

- HTML report (Components 16, 17).
- JUnit XML (Component 18).
- A Markdown report variant for non-PR contexts (e.g., terminal-rendered Markdown). Today's terminal output is rich-styled text from Component 05; the Markdown form is for elsewhere.
- Configurable per-kind emoji or template overrides. Future polish; not in v1.
- A separate "compact" or "verbose" Markdown mode beyond what's already produced. The current shape is the agreed shape.
- Localization. English only.
- Schema-validated Markdown output (Markdown isn't validated against the JSON schema).
- Internal links (e.g., bullets that link to a detailed section). Markdown doesn't have stable anchors; keep flat.

## Open questions

- [ ] **Q1:** Should rename changes be in their own section or merged into "Other changes"?
  **Proposed:** Their own section ("Renames"), even if only 1. They're conceptually different from regular changes (they consolidate add+remove pairs) and users specifically look for them when reviewing refactoring PRs. Separate section is the clearer mental model.

- [ ] **Q2:** Should `<details>` HTML be used or pure Markdown for the Layer 0 collapsible? GitHub supports `<details>`; some other renderers don't.
  **Proposed:** Use `<details>`. GitHub is the primary target. Other Markdown renderers either degrade gracefully (showing the content as plain text) or treat it as HTML, which is acceptable. The alternative — keeping the section always-expanded — would clutter the report when there are 50+ unexplained Layer 0 changes.

- [ ] **Q3:** Should the footer include a link to the JSON output, and if so, where does it point?
  **Proposed:** Yes, but as plain text (not a link). The Markdown output may be posted anywhere; we can't predict where the JSON lives. Phrase as: `*Run with --format json for machine-readable output*` after the schema reference. No URL.

If you have a preference, override before implementing; otherwise proceed with the proposed answers.
